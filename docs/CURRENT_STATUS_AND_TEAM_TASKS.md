# Поточний статус і задачі команди FlowMind

Актуально станом на 3 липня 2026 року.

## 1. Стан проєкту

FlowMind перебуває на стадії робочого pre-MVP. Основний цикл уже
працює:

```text
SUMO
  → TraCI-телеметрія
  → аналіз транспортної зони
  → рішення контролера
  → керування штатними фазами
  → метрики
  → Streamlit
```

Проєкт можна встановити, запустити на карті Рівного, порівняти режими та
показати автоматичний виїзд швидкої.

## 2. Що вже готово

### Симуляція

- реальна SUMO-карта центральної частини Рівного;
- зона з 6 пов'язаних світлофорів;
- 8 сфокусованих маршрутів через 2–4 контрольовані перехрестя;
- генератор трафіку для вибраної зони;
- однакові параметри запуску для порівняння режимів.

### Керування світлофорами

- Fixed Mode;
- Local Adaptive Mode;
- FlowMind Area Balance;
- оцінювання черг і downstream-заповненості;
- мінімальна та максимальна тривалість зеленого;
- штатні жовті й all-red переходи SUMO;
- базовий пріоритет фази для швидкої.

### Швидка

- автоматичне додавання через TraCI;
- налаштування старту, лікарні та часу виїзду;
- автоматичне прокладання одного маршруту;
- окремий тип і червоний колір у SUMO GUI;
- вимірювання фактичного departure, arrival та Emergency ETA;
- передавання маршруту швидкої в Priority Flow.

### Метрики та інтерфейс

- CSV та JSON з результатами;
- час поїздки, очікування, черги, зупинки й середня швидкість;
- gridlock risk;
- Emergency ETA;
- Streamlit-дашборд після завершення симуляції;
- окремий графічний менеджер запуску `project_manager.py`.

### Документація і перевірки

- встановлення з нуля на Windows;
- створення SUMO-карти з OpenStreetMap;
- окрема інструкція для `simulation/new_area/map.osm`;
- 22 автоматичних тести;
- автоматичний builder `tools/build_sumo_map.py` для локальних
  `.osm`-файлів;
- успішний headless-прогін нової карти в SUMO 1.27.1.

## 3. Стан `simulation/new_area`

Зараз наявні:

```text
simulation/new_area/
├── map.osm
├── osm.net.xml.gz
└── README.md
```

`map.osm` успішно конвертується. Мережа містить потрібні світлофори
центральної зони.

Для завершення підключення ще потрібно створити:

```text
osm.poly.xml.gz
central_zone.json
focused.rou.xml
focused.sumocfg
focused.manifest.json
emergency.json
```

Старі точки швидкої не підходять до цієї карти: станція екстреної
допомоги та лікарня розташовані за її межами. Потрібно або розширити
OSM-область, або вибрати нові валідні edge ID всередині карти.

## 4. Що ще не готово

Ці можливості не можна заявляти як завершені:

- повний рухомий зелений коридор;
- 3–5 альтернативних маршрутів швидкої;
- автоматичний вибір маршруту з найменшим прогнозованим ETA;
- Corridor Manager зі станами PREPARE, GREEN, CLEARANCE і RECOVERY;
- окремий Safety Validator;
- live-телеметрія у Streamlit під час симуляції;
- статистично доведена перевага FlowMind;
- навчена ML або reinforcement learning модель;
- керування реальними міськими світлофорами.

## 5. Найближча спільна ціль

Наступна демонстраційна версія повинна показувати два сценарії:

1. FlowMind зменшує або краще розподіляє черги порівняно з Fixed і
   Local Adaptive.
2. Швидка отримує безпечний рухомий зелений коридор, після чого
   світлофори повертаються до звичайного зонального керування.

Для цього команда спочатку завершує карту й baseline, потім зелений
коридор, а вже після цього live-візуалізацію та ML.

## 6. Розробник 1 — Traffic Control і експерименти

Зона відповідальності:

```text
карта → трафік → контролер → метрики → benchmark
```

### Задачі зараз

1. Завершити `simulation/new_area` за інструкцією в її `README.md`.
2. Перевірити `central_zone.json` і покриття всіх 6 світлофорів.
3. Згенерувати `focused.rou.xml`, config і manifest.
4. Виконати 120-секундний headless smoke test.
5. Запустити Fixed, Local Adaptive і FlowMind з однаковим seed.
6. Перевірити, що результати різних запусків не перезаписуються.
7. Підготувати сценарії:
   - normal;
   - rush hour;
   - congestion або incident.
8. Автоматизувати серію запусків для seed `41–50`.
9. Додати в summary:
   - назву сценарію;
   - seed;
   - traffic demand;
   - duration;
   - версію карти.
10. Порахувати median і p95 для основних KPI.

### Результат роботи

- відтворюваний benchmark трьох режимів;
- таблиця з реальними результатами;
- один стабільний сценарій для презентації;
- автоматичні тести для нової логіки.

### Файли у власності

- `simulation/`;
- `tools/generate_focused_traffic.py`;
- `flowmind/traffic_state.py`;
- `flowmind/signal_policy.py`;
- `flowmind/metrics.py`;
- benchmark-скрипти в `experiments/`.

## 7. Розробник 2 — Emergency і платформа

Зона відповідальності:

```text
маршрут швидкої → зелений коридор → safety → API/telemetry
```

### Задачі зараз

1. Додати `flowmind/emergency_router.py`.
2. Будувати щонайменше 3 валідні альтернативні маршрути.
3. Для кожного маршруту повертати:
   - edge ID;
   - послідовність світлофорів;
   - довжину;
   - базовий travel time;
   - queue penalty;
   - прогнозований ETA.
4. Зберігати всі альтернативи й причину вибору маршруту.
5. Додати `flowmind/corridor_manager.py`.
6. Реалізувати мінімальну state machine:

```text
NORMAL → PREPARE → GREEN_WINDOW → CLEARANCE → RECOVERY → NORMAL
```

7. Не встановлювати довільні signal states: використовувати штатні фази
   SUMO.
8. Додати timeout і fallback, якщо швидка зникла або не виїхала.
9. Додати тести переходів між станами без запуску SUMO.
10. Після стабілізації додати live-телеметрію, але не починати з неї.

### Результат роботи

- швидка може обрати один із кількох маршрутів;
- зелена хвиля рухається попереду неї;
- після проїзду кожне перехрестя повертається до FlowMind;
- помилка emergency-логіки не зупиняє звичайний контролер.

### Файли у власності

- `flowmind/emergency_vehicle.py`;
- `flowmind/emergency_router.py`;
- `flowmind/priority_flow.py`;
- `flowmind/corridor_manager.py`;
- майбутній `flowmind/safety_validator.py`;
- emergency-параметри в `experiments/run_experiment.py`.

Зміни в `flowmind/experiment.py` потрібно узгоджувати з розробником 1,
оскільки це спільна точка інтеграції.

## 8. Дизайнер — графіка і презентація

Дизайнер не зобов'язаний редагувати код. Його задача — підготувати
візуальне пояснення на основі фактичної роботи системи.

### Задачі зараз

1. Схема зони з 6 підписаними перехрестями.
2. Окремі кольори для:
   - Fixed;
   - Local Adaptive;
   - FlowMind;
   - Emergency Priority.
3. Іконки автомобіля, черги, світлофора, швидкої та лікарні.
4. Схема принципу роботи:

```text
датчики → FlowMind → рішення → світлофори → результат
```

5. Ілюстрація зеленого коридору зі станами підготовки, проїзду й
   відновлення.
6. Макет live-дашборду:
   - карта;
   - активний режим;
   - маршрут швидкої;
   - ETA;
   - KPI;
   - стан найближчого світлофора.
7. Презентація 16:9 на 7–9 слайдів.
8. Обкладинка та 3–5 скриншотів для Telegram-звіту.
9. Коротка графіка `Fixed → Local → FlowMind`.
10. Після стабільного запуску — монтаж demo-відео на 45–60 секунд.

### Обмеження

- не вигадувати KPI, яких немає у результатах;
- не показувати повний зелений коридор як готовий до його реалізації;
- використовувати однакові назви режимів у всіх матеріалах;
- зберігати вихідні файли та експортовані PNG/SVG окремо.

Рекомендована директорія:

```text
assets/presentation/
```

## 9. Молодший учасник — QA, сценарії та документація

Задачі мають давати практику з Git, SUMO і тестуванням без ризику
пошкодити основний контролер.

### Задачі зараз

1. Встановити проєкт за інструкцією під наглядом розробника.
2. Запустити:

```bash
python project_manager.py --diagnose
python experiments/run_fixed.py --duration 120
python experiments/run_local_adaptive.py --duration 120
python experiments/run_flowmind.py --duration 120
```

3. Для кожного режиму записати:
   - чи завершився запуск;
   - середню чергу;
   - час очікування;
   - кількість завершених поїздок;
   - повідомлення про помилки.
4. Запустити demo зі швидкою та перевірити:
   - поява червоної швидкої;
   - фактичний виїзд;
   - прибуття;
   - показ Emergency ETA у Streamlit.
5. Зробити однакові скриншоти для трьох режимів.
6. Перевірити кнопки `project_manager.py`.
7. Створити QA-звіт:

```text
docs/qa/QA_REPORT.md
```

8. Описувати помилку за шаблоном:
   - що запускав;
   - точна команда;
   - що очікував;
   - що сталося;
   - текст помилки;
   - скриншот.
9. Виправляти лише документацію або прості конфіги після погодження.
10. Кожну зміну передавати одному з розробників на review.

### Результат роботи

- повторюваний ручний QA-чекліст;
- список знайдених проблем;
- перевірені команди документації;
- скриншоти для дизайнера.

## 10. Порядок роботи без конфліктів

Перед початком нових гілок потрібно спочатку зафіксувати й запушити
поточні зміни `feature/pre-mvp`.

Після цього:

```text
feature/benchmark-baseline     — розробник 1
feature/emergency-corridor     — розробник 2
docs/presentation-assets       — дизайнер або відповідальний за assets
docs/qa-checklist              — молодший учасник
```

Правила:

- не комітити `.venv`, `results/` і тимчасові файли;
- не перегенеровувати чужі XML-файли без погодження;
- один pull request має закривати одну логічну задачу;
- перед merge запускати всі тести;
- не змішувати алгоритм, графіку й документацію в одному великому
  коміті;
- усі KPI для презентації брати зі збереженого benchmark.

## 11. Порядок на найближчі три етапи

### Етап 1 — стабілізація

- завершити `new_area`;
- зафіксувати сценарії та seed;
- отримати benchmark;
- завершити QA-чекліст.

### Етап 2 — зелений коридор

- альтернативні маршрути;
- Corridor Manager;
- safety і fallback;
- порівняння ETA з priority та без priority.

### Етап 3 — презентація

- live-телеметрія;
- фінальні KPI;
- слайди;
- скриншоти;
- demo-відео;
- репетиція запуску з чистого середовища.

## 12. Формат короткого щоденного звіту

Кожен учасник пише три пункти:

```text
Зроблено:
План далі:
Блокери:
```

Звіт має містити посилання на commit, pull request, файл, скриншот або
результат запуску. Формулювання «працюю над задачею» без перевірюваного
результату недостатньо.
