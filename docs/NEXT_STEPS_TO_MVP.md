# Подальші кроки для досягнення мети FlowMind Rivne

Актуально станом на 30 червня 2026 року.

## 1. Аналіз поточного стану

Проєкт не відійшов від початкової ідеї. Основне ядро вже реалізоване:

```text
реальна зона Рівного
        ↓
сфокусований транспортний потік
        ↓
SUMO + TraCI
        ↓
Fixed / Local Adaptive / FlowMind
        ↓
метрики та дашборд
```

FlowMind уже керує групою з шести пов’язаних світлофорів і враховує стан
наступних ділянок дороги. Це відповідає головній меті зонального
балансування.

Поточні проблеми не змінюють напрям проєкту. Вони показують, які частини
ще потрібно завершити:

1. Priority Flow поки є hook, а не повним зеленим коридором.
2. Автоматична швидка готова, але поки використовується один маршрут.
3. Немає навченої прогнозної моделі.
4. Перевага FlowMind ще не підтверджена серією експериментів.
5. Дашборд не отримує live-телеметрію.
6. Немає API для керування сценаріями.

## 2. Кінцева мета MVP

MVP можна вважати готовим, коли система демонструє два завершені
сценарії.

### Сценарій A — зональне балансування

```text
У зоні утворюється перевантаження
        ↓
Fixed накопичує черги
        ↓
Local Adaptive частково переносить затор
        ↓
FlowMind враховує downstream і балансує всю зону
        ↓
результат підтверджується метриками
```

### Сценарій B — швидка допомога

```text
У симуляції з’являється швидка
        ↓
система знаходить 3–5 маршрутів
        ↓
обирає маршрут з найкращим прогнозованим ETA
        ↓
послідовно готує світлофори
        ↓
швидка проходить зелений коридор
        ↓
зона безпечно повертається до FlowMind
```

Для обох сценаріїв потрібно показати:

- роботу на карті;
- рішення контролера;
- часові графіки;
- порівняння з базовим режимом;
- числовий результат;
- відсутність небезпечних фаз.

## 3. Правильний порядок реалізації

Роботи потрібно виконувати в такій послідовності:

1. Зафіксувати стабільний експериментальний baseline.
2. Реалізувати Emergency Router з альтернативними маршрутами.
3. Реалізувати Corridor Manager.
4. Додати safety validation і режим відновлення.
5. Провести серію порівняльних експериментів.
6. Додати live API й live-дашборд.
7. Зібрати дані та навчити прогнозну модель.
8. Додати прогноз у FlowMind або MPC.
9. Підготувати презентаційний сценарій.

Не варто починати з LLM або reinforcement learning. Вони не закриють
відсутність маршрутизації швидкої, safety layer і якісних експериментів.

## 4. Етап 1 — стабільний baseline

### Завдання

- зафіксувати тривалість основного сценарію;
- зафіксувати інтенсивність трафіку;
- додати параметри сценарію в окремий конфіг;
- забезпечити однаковий seed для трьох режимів;
- записувати версію сценарію в результати;
- додати окремі вихідні папки для кожного запуску;
- не перезаписувати результати попередніх експериментів;
- додати команду запуску серії експериментів.

Рекомендована структура:

```text
simulation/scenarios/
├── normal.json
├── rush_hour.json
├── incident.json
└── emergency.json

results/
└── run_<date>_<seed>/
    ├── fixed/
    ├── local/
    └── flowmind/
```

### Критерій готовності

- один seed дає відтворюваний результат;
- усі режими використовують однаковий попит;
- результати одного запуску не перезаписують інші;
- одна команда запускає Fixed, Local і FlowMind;
- у summary записані seed, сценарій, duration і traffic demand.

## 5. Етап 2 — автоматичне створення швидкої — виконано

### Новий модуль

```text
flowmind/emergency_vehicle.py
```

### Реалізовано

- створити окремий SUMO `vType` для швидкої;
- задати колір, розмір, швидкість і параметри руху;
- додавати швидку через TraCI в заданий момент;
- задавати стартову позицію та пункт призначення;
- записувати момент виїзду, прибуття та повний ETA;
- показувати швидку окремим кольором у SUMO GUI;
- додати CLI-параметри для запуску emergency-сценарію.
- автоматично запускати Streamlit зі статистикою після demo-симуляції.

Приклад:

```bash
python experiments/run_flowmind.py \
  --duration 900 \
  --emergency \
  --emergency-depart 300 \
  --gui
```

### Критерій готовності

- швидка автоматично з’являється у визначений момент;
- має валідний маршрут;
- відображається окремим кольором;
- система фіксує її departure time, arrival time та ETA;
- звичайний сценарій працює без ручного введення vehicle ID.

## 6. Етап 3 — Emergency Router

### Новий модуль

```text
flowmind/emergency_router.py
```

### Принцип

Emergency Router повинен будувати декілька маршрутів і оцінювати не лише
довжину дороги.

```text
route_cost =
free_flow_travel_time
+ predicted_delay
+ queue_penalty
+ blocked_edge_penalty
+ corridor_activation_cost
+ civil_traffic_impact
```

### Завдання

- представити дорожню мережу через NetworkX;
- отримувати актуальну вагу ребер із TraCI;
- реалізувати time-dependent A*;
- отримувати 3–5 альтернатив через Yen K-shortest paths;
- відкидати заблоковані та недоступні маршрути;
- визначати послідовність світлофорів на кожному маршруті;
- оцінювати час підготовки зеленого коридору;
- вибирати маршрут із мінімальною загальною вартістю;
- зберігати альтернативи й причину вибору.

### Критерій готовності

- система будує не менше трьох валідних альтернатив;
- кожен маршрут містить список світлофорів і прогнозований ETA;
- зміна затору може змінити вибраний маршрут;
- результат відтворюється за однакового стану симуляції;
- обраний маршрут можна відобразити на дашборді.

## 7. Етап 4 — Corridor Manager

### Новий модуль

```text
flowmind/corridor_manager.py
```

### State machine

```text
NORMAL
  ↓
PREPARE
  ↓
GREEN_WINDOW
  ↓
CLEARANCE
  ↓
RECOVERY
  ↓
NORMAL
```

### Поведінка станів

#### NORMAL

Зона працює в режимі FlowMind Area Balance.

#### PREPARE

- визначається ETA швидкої до наступного перехрестя;
- завершується поточна безпечна фаза;
- звільняється конфліктний рух;
- виконується жовтий та all-red перехід.

#### GREEN_WINDOW

- потрібний напрямок отримує зелений;
- фаза утримується в дозволених межах;
- контролер стежить за фактичним наближенням швидкої.

#### CLEARANCE

- система підтверджує проїзд швидкої;
- завершує зелений без різкого перемикання;
- очищає перехрестя.

#### RECOVERY

- світлофор поступово повертається до штатної програми;
- FlowMind тимчасово компенсує накопичені бокові черги;
- після стабілізації повертається NORMAL.

### Критерій готовності

- зелений коридор рухається попереду швидкої;
- одночасно не відкриваються конфліктні напрямки;
- жовті та all-red фази не пропускаються;
- після проїзду швидкої не залишається зависла фаза;
- система повертається до FlowMind без перезапуску симуляції.

## 8. Етап 5 — Safety Validator

### Новий модуль

```text
flowmind/safety_validator.py
```

### Перевірки

- min green;
- max green;
- yellow duration;
- all-red duration;
- заборона конфліктних green links;
- заборона переходу через декілька фаз;
- downstream occupancy limit;
- максимальний час priority override;
- fallback при втраті швидкої;
- fallback при помилці контролера;
- fallback при недоступності API або AI-моделі.

### Правило

```text
Controller або AI пропонує план
        ↓
Safety Validator перевіряє план
        ↓
TraCI застосовує тільки дозволений план
```

### Критерій готовності

- жодне рішення не застосовується без validation;
- для кожного відхиленого плану записується причина;
- при помилці система повертається до штатної SUMO-програми;
- safety layer не залежить від LLM, API або мережі.

## 9. Етап 6 — доказове порівняння режимів

### Сценарії

Потрібно підготувати щонайменше:

1. Normal traffic.
2. Rush hour.
3. Central congestion.
4. Blocked downstream.
5. Road incident.
6. Emergency without green corridor.
7. Emergency with green corridor.

### Методика

Базовий focused benchmark уже реалізований у
`experiments/run_evaluation.py`. Кожна з 30–50 replicate-пар містить
`static_fixed`, `sumo_actuated`, `local` і `flowmind` з однаковими seed,
duration, demand/network/config hashes та фактичним emergency route. Інші
сценарії з переліку вище мають підключатися як окремі manifests, не змішуючись
в одну статистичну вибірку.

### Метрики

- average travel time;
- average waiting time;
- average queue;
- maximum queue;
- throughput;
- stops count;
- blocked outgoing share;
- emergency ETA;
- civil traffic penalty;
- recovery time після швидкої;
- кількість emergency braking;
- кількість teleport.

### Статистика

`flowmind/evaluation.py` рахує mean paired difference, 95% Student-t CI,
двосторонній paired t-test і Cohen's dz для FlowMind проти кожного baseline.
Відсутні значення залишаються `null`, зменшують paired sample count і можуть
перевести gate у `insufficient_data`.

### Новий скрипт

```text
experiments/run_evaluation.py
```

Приклад:

```bash
python experiments/run_evaluation.py \
  --replicates 30 \
  --duration 1800 \
  --workers 4 \
  --evaluation-id rivne_full_v1
```

### Критерій готовності

- результати не базуються на одному вдалому запуску;
- можна повторити весь benchmark однією командою;
- звіт містить paired CI/tests і regression gates;
- презентаційні твердження підтверджуються збереженими даними;
- негативні результати також не приховуються.

### Важливе обмеження

API не повинно напряму встановлювати довільний колір світлофора.

Правильний потік:

```text
API request
    ↓
validated command
    ↓
Controller / Corridor Manager
    ↓
Safety Validator
    ↓
TraCI
```

### Критерій готовності

- сценарій можна запустити й зупинити через API;
- поточний стан зони доступний у JSON;
- швидку можна відправити через validated request;
- live-телеметрія передається через WebSocket;
- помилка клієнта не зупиняє SUMO-процес.

### Потрібно додати

- карту центральної зони;
- поточні позиції автомобілів;
- окрему іконку швидкої;
- стан кожного світлофора;
- чергу на кожній вхідній смузі;
- heatmap завантаженості;
- поточний режим;
- активний маршрут швидкої;
- альтернативні маршрути;
- ETA до наступного світлофора;
- state Corridor Manager;
- live-графіки;
- кнопку запуску сценарію;
- кнопку dispatch emergency.

### Критерій готовності

- дані оновлюються без перезавантаження сторінки;
- карта відповідає стану SUMO;
- швидка та її маршрут візуально відрізняються;
- можна одночасно бачити симуляцію, рішення й KPI;
- дашборд продовжує показувати останній стан при короткій втраті API.

## 12. Етап 9 — прогнозна ML-модель

ML потрібно додавати після того, як стабільно збираються дані.

### Дані для навчання

Кожні 5 секунд зберігати:

- queue length;
- vehicle count;
- occupancy;
- mean speed;
- waiting time;
- current phase;
- spent phase duration;
- arrivals за останні 30 секунд;
- departures за останні 30 секунд;
- downstream occupancy;
- scenario;
- simulation seed;
- timestamp.

### Target

Прогноз на 30, 60 і 90 секунд:

- майбутня черга;
- майбутня occupancy;
- ризик downstream blocking;
- очікуваний travel time ребра.

### Перша модель

Рекомендовано:

```text
LightGBM або XGBoost
```

Переваги:

- працює на CPU;
- швидко навчається;
- легко пояснюється;
- підходить для невеликої кількості даних;
- має feature importance.

### Не починати одразу з

- великої нейромережі;
- LLM як traffic predictor;
- multi-agent RL;
- end-to-end моделі без safety layer.

### Критерій готовності

- є окремі train, validation і test seed;
- прогноз кращий за naive baseline;
- вимірюються MAE та RMSE;
- inference вкладається в цикл контролера;
- при помилці моделі FlowMind працює без прогнозу.

## 13. Етап 10 — MPC із прогнозом

Після готовності прогнозу можна перейти від реактивного pressure-based
контролера до короткострокового планування.

### Новий модуль

```text
flowmind/mpc_controller.py
```

### Горизонт

```text
60–90 секунд
```

### Objective

```text
minimize:
    total_waiting_time
  + queue_imbalance
  + downstream_blocking_penalty
  + phase_switch_penalty
  + emergency_eta_penalty
  + civil_traffic_disruption
```

### Constraints

- min/max green;
- yellow та all-red;
- допустимий порядок фаз;
- downstream capacity;
- corridor reservations;
- максимальна тривалість priority override.

### Критерій готовності

- рішення вкладається в доступний час;
- план проходить Safety Validator;
- MPC порівнюється з поточним Area Pressure;
- покращення підтверджено benchmark, а не одним запуском;
- при timeout використовується поточний pressure-based fallback.

## 14. Роль LLM

LLM не повинна виконувати real-time control.

### Дозволені задачі

- прийняти текстову команду диспетчера;
- перетворити її у validated JSON;
- пояснити вибір маршруту;
- пояснити рішення FlowMind;
- сформувати звіт про інцидент;
- підготувати короткий опис метрик;
- викликати безпечні API tools.

### Заборонені задачі

- напряму встановлювати signal state;
- обходити Safety Validator;
- генерувати довільні фази;
- бути єдиним джерелом маршруту швидкої;
- блокувати локальний контролер при недоступності API.

### Варіанти

Локально:

```text
gpt-oss-20b
```

Через API:

```text
gpt-5.4-mini — основний варіант
gpt-5.5 — складне планування та демонстрація
```

LLM інтегрується після готовності Emergency Router, Corridor Manager,
Safety Validator та API.

- інтеграція прогнозу;
- MPC або predictive pressure.

Результат: можна чесно заявляти про ML-прогнозування.

## 17. Пріоритети

### Must have для сильної презентації

1. Автоматична швидка.
2. Повний зелений коридор.
3. Безпечне повернення до FlowMind.
4. Серія benchmark-запусків.
5. Emergency ETA і civil traffic penalty.
6. Візуалізація маршруту та світлофорів.
7. Резервне відео демонстрації.

### Should have

1. FastAPI.
2. WebSocket live telemetry.
3. Live-дашборд.
4. Сценарій ДТП.
5. Автоматичний генератор звіту.

### Could have

1. LightGBM forecast.
2. MPC.
3. LLM-диспетчер.
4. Голосова команда.
5. Multi-agent RL як research-прототип.

## 18. Що не варто робити до завершення ядра

- не тренувати RL без стабільного baseline;
- не підключати LLM до прямого керування фазами;
- не розширювати симуляцію на все місто;
- не створювати мобільний застосунок;
- не витрачати час на 3D-візуалізацію;
- не заявляти недоведені відсотки покращення;
- не приховувати сценарії, де FlowMind програє;
- не будувати production-інфраструктуру до завершення MVP.

## 19. Definition of Done

MVP готовий, якщо одночасно виконані всі умови:

- працює зона з 4–6 реальних світлофорів;
- Fixed, Local і FlowMind використовують однаковий попит;
- FlowMind враховує downstream;
- швидка створюється автоматично;
- будується не менше трьох маршрутів;
- Corridor Manager створює рухомий зелений коридор;
- Safety Validator перевіряє кожне рішення;
- після проїзду система повертається до NORMAL;
- є emergency ETA та civil traffic penalty;
- виконано не менше 10 seed для кожного режиму;
- пораховано median і p95;
- є live-візуалізація або стабільна синхронна демонстрація;
- усі ключові модулі покриті тестами;
- запуск на Windows описаний і перевірений;
- підготовлено резервне відео.

## 20. Найближчий конкретний крок

Наступна задача, яку потрібно реалізувати першою:

> Реалізувати Emergency Router, який будує 3–5 альтернативних маршрутів
> для вже автоматично створюваної швидкої, оцінює ETA, затори й вартість
> підготовки зеленого коридору та обирає найкращий маршрут.

Після цього можна переходити до Corridor Manager.
